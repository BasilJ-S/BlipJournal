Blip Journal · Issue #57

A completed entry must stay completed

The detail screen retained an old draft value after Done. It still offered Continue, and the runner trusted that stale value. The original report showed lost completion; current main already blocks the overwrite in storage, but still allowed the misleading reopen.

Before · the bug

Open draft detail → Continue
↓
Finish the entry → Done
↓
Detail still says Draft and offers Continue
↓
Runner opens from stale value; saving hits the storage guard

After · the fix

Finish the entry → Done
↓
Detail reloads the persisted entry by ID
↓
Completed date appears; Continue disappears
↓
Stale or deleted entry values are refused on resume

Why this works

Store.entry reads the authoritative row by ID. Both detail refresh and EntryDraft resume use it. Continue is hidden until detail has successfully loaded. The existing storage completion guard still protects against completion racing with a later save.

Test evidence

RED · before the fix

Both regression tests failed: stale completed and deleted entry values opened a runner instead of throwing.

GREEN · after the fix

The full app suite passes, including detail reload and persisted-answer checks. All 445 core tests pass, including lookup before save, after completion, and after deletion.

Simulator-hosted tests verify the detail read path and runner initialization. No repeated end-to-end navigation test is claimed. Current main already prevented the original completion overwrite; this PR closes the remaining stale UI and initialization paths.
