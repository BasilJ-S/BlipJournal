Blip Journal · Issue #60

Option changes must not erase pending question edits

Question fields save on Save question, but options save immediately. Each option mutation refreshed the screen and silently restored the old question fields.

Before · the bug

Change the question label, Required, or custom options
↓
Add, rename, reorder, or archive an option
↓
The option saves and triggers a revision refresh
↓
Pending question fields revert; Save writes the old values

After · the fix

Edit fields in a question draft
↓
Save an option immediately
↓
Refresh current options; preserve the same question's draft
↓
Save merges pending fields into the latest question

Why this works

Core QuestionEditDraft initializes once per question ID. Repeated loads for that ID preserve pending values; switching to another question initializes its fields. Applying the draft retains the latest option list and only includes configuration relevant to the question kind.

Test evidence

RED · before the fix

All four option-mutation cases failed, with 24 failed expectations across pending fields and persisted values, after extracting the existing reset-on-refresh behavior without changing it.

GREEN · after the fix

All 446 core tests and the full app suite pass. Regression cases cover add, rename, reorder, and archive; each verifies both pending fields and the saved question, while preserving the updated options. A separate test checks switching question IDs.

These tests exercise the same draft load and save path now used by the editor and inspect persisted state. No repeated touch-driven editor workflow is claimed. Concurrent external field edits are not merged into an open local draft.
